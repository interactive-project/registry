# Plugin registration and independent resolution v1

EngineManifest is serializable JSON: manifestVersion 1.0.0, namespaced id, pluginVersion, Protocol activity type, explicit protocolVersions and exact per-domain generation entries. Each entry reuses Protocol GenerationEntry with type, activitySchemaVersion, owning schemaId, all seven capability declarations and required capabilities/permissions. Entries must match the manifest type, be unique by exact version and satisfy Protocol catalog semantics. The reference supports protocol 1.0.0 only; package versions are independent. schemaId is an offline trusted registry identity, not a remote fetch command.

Executable functions are separate live EnginePorts: createEngine conforms to Protocol EngineDriver.create, and evaluate accepts a retained EngineSession and returns a Protocol Result synchronously or asynchronously. Evaluation may delegate to session.evaluate; it never means user code is evaluated inside Registry. Factories, services, signals and native objects never enter a portable manifest. Live ports are captured by function identity; mutating the original ports object does not replace a registered factory. Host code is trusted, not a sandbox.

RendererManifest is separate: activity type, host react/vue/svelte/dom, protocolVersions, exact activitySchemaVersions, rendererContractVersion 1.0.0, plugin id/version. RendererPorts.createRenderer accepts a live session, opaque host mount and optional host services, returning update/dispose lifecycle hooks. Registry owns no DOM or framework mount meaning. Engine resolution does not inspect or load renderer registrations; renderers do not grant capability/permission to execute an engine.

## Exact keys, conflicts and lifecycle

An engine slot is (activity type, protocol version, activity schema version). A renderer slot adds host kind. register checks a bounded frozen JSON copy through a trusted synchronous validator before adding any records. Optional validateEngineManifest/validateRendererManifest provide structural/semantic schema validation via Ajv; callbacks are side-effect-free and async/missing/throwing validation fails closed. Admission has no factory execution, dynamic import, network or renderer effect.

Registration IDs are unique across both kinds. Duplicate IDs report registry.duplicate. Any overlapping engine/renderer slot reports registry.conflict, with the existing public registration ID and relevant path. A manifest claiming multiple slots is accepted atomically or none are added. At most 1,000 records, 32 versions/entries per manifest and 1 MiB JSON are supported, with bounded depth/collections/strings/nodes. No implicit priority, overwrite, last-registration-wins or undocumented override exists. Replacement requires explicitly unregistering the old handle, then validating/registering the new manifest. If replacement fails, the caller decides whether to re-register the old descriptor; Registry never silently downgrades versions.

Registration returns an idempotent unregister closure capturing that record's identity. It removes future lookups only. A stale closure cannot remove a later registration reusing the same public id. Returned resolutions capture immutable manifest/ports, so already-created sessions remain owned by their original engine and continue after unregistration. Removing a renderer likewise cannot dispose a running mount; its host explicitly calls dispose. Registry disposal clears registration/index maps and rejects future registration/lookups but never disposes caller-owned sessions or renderers.

Lookup requires exact contract/domain versions and, for a renderer, exact host kind. Missing engines/renderers report separate codes. Headless engine use requires no renderer registration at all. Version negotiation, lazy import caching, cancellation, required-driver availability and capability-aware selection belong to registry#2; serializable catalog export belongs to #3. A manifest advertisement alone cannot authorize host services or attest actual conformance.

## Compatibility and verification

Protocol has no reverse Registry dependency. Existing Protocol wire schemas remain unchanged. Registry 0.1.0 implements manifestVersion 1.0.0 in repository; npm publication is separate. No prior released registry-manifest format needs migration. Closed manifest changes and renderer lifecycle changes require an explicit compatibility decision and oldest/newest contract gates.

npm test validates the fixture quiz registration and separate React/Vue/Svelte/DOM host declarations. All four resolve the identical engine function without invoking renderer factories during lookup. The same live fixture session is rendered through four host-port stand-ins; the engine imports no frameworks/browser APIs. These fixtures verify the registration seam, not actual UI framework integrations or production quiz release conformance. The fixture claims no resumability/AI generation and uses explicit fixture-only domain 0.0.1. Tests cover duplicate/conflicting slots, invalid/duplicate/mismatched entries, unknown versions, missing ports, immutable input/ports, explicit replacement/stale handles, retained sessions, async validator failure, disposal and ES2022-only types. Real domain/host implementations will supply their own runtime and browser gates.
