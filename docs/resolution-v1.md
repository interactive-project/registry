# Version negotiation and lazy loading v1

The optional resolution entry operates on captured Registry registrations. Registration remains exact/atomic; listEngines/listRenderers expose immutable captured descriptors, never factories instantiated during enumeration.

## Explicit version selection

A query names activity type and exact protocolVersion, with either activityVersion.exact or a half-open supported range {min,maxExclusive}. This is deliberately not an ambiguous npm caret/tilde/string expression. Range comparisons use numeric three-part tuples, including arbitrarily large decimal components without IEEE-754 precision loss. Candidates must be explicitly advertised by a registered engine, within the range AND share the minimum's major version. A range spanning majors still cannot implicitly upgrade: request another major explicitly. Authored activitySchemaVersion is an exact wire version; range discovery never rewrites an authored document or migrates it.

Choose the highest eligible domain version; registration ID lexicographic order is the stable secondary tie-break (overlapping exact slots already reject at registration). No registration order, clock, module import completion or unverified package version influences selection. A requested renderer host must have a matching exact protocol/domain registration; otherwise the candidate is rejected, allowing an older eligible candidate with a compatible renderer. Headless queries omit host and never resolve a renderer.

Every discarded same-type entry explains protocol/version/permission/capability/driver/renderer failure with registration ID, domain version, safe code and optional required capability/driver/permission name. A successful result includes both the selected descriptor and rejected alternatives. With no candidate, resolution.unavailable is explicit; malformed range/policy/query is resolution.invalid. No factory, asset lookup, network or UI is executed.

Required capabilities are the union of the entry's requirements and host-requested capabilities. Declarations must support them, all conditional requiredDrivers must be in the host's availableDrivers, and requiredPermissions must be explicitly true in captured host policy (network/execution/media default denied). offline additionally rejects any required network permission even if network is authorized. Declaring deterministic/resumable/evaluable/AI behavior does not grant execution or make an absent WASM driver available. Core still performs generated/config-dependent semantic requirements before actual engine resolution.

## Trusted asynchronous loader

createPluginLoader accepts trusted live definitions: namespaced id, exact protocolVersions, dependency edges with their own exact protocolVersions, and a separate load(signal) function. The host owns module URLs/imports, offline/network policy and driver probing; portable data cannot register code or request arbitrary imports. Selection/permission checks occur before the host invokes loading. Loading returns live opaque ports which the host must register through validated manifests; it does not silently install modules or partially register a dependency graph.

At construction reject missing/duplicate dependencies, cycles, graph depth over 32 and any transitive protocol intersection that is empty. Each requested protocol must satisfy the node, every dependency and every edge. Reject conflicts rather than loading versions that negotiate different shared protocols. Up to 1,000 definitions, 32 versions/edges each, 128 in-flight operations, 128 waiters per operation and 128 successful cache entries are supported. Cache uses a deterministic LRU eviction policy; evicted live values may be reloaded, but caller-owned sessions/ports stay valid. Definitions are captured; later mutation of descriptor arrays cannot change the graph.

Concurrent callers for one (id,protocolVersion) share one loader/dependency operation. Each caller cancellation removes only its own waiter. The shared signal aborts only when no waiter remains, on timeout or disposal. Dependency requests participate in the same independent-waiter rules. An already-cancelled caller fails without loading. Successful values cache; failures/cancelled/timed-out results do not. Late noncooperative results never populate an aborted/disposed cache or overwrite a newer operation.

The deadline covers dependency and own loading (default 30,000 ms, host may set 1..60,000). Timeout aborts the shared signal and rejects with loader.timeout. Host-configured retries default zero and are bounded to three retries; only own load failure is retried under the same deadline/signal. A later explicit request may retry a failed operation. Native errors are replaced with safe static loader.failure. The host must make load idempotent and clean up partial resources before retry. Abort is cooperative: JavaScript cannot stop an arbitrary module import or roll back its external side effects. A timed-out importer may still execute host code, so loaders must check the signal before publishing handles/registering resources. Registry performs no stale auto-registration.

Disposal aborts all shared operations, clears caches and rejects future requests. Loaded ports remain caller-owned; disposal does not destroy sessions or renderer mounts. CancellationSignal is Protocol's structural live port; public declarations compile with ES2022 only, with no DOM type dependency.

## Verification and compatibility

Tests exercise unsupported exact/protocol versions, range selection without major upgrades, permission rejection, missing renderer, absent fixture WASM driver, offline-only selection and selected-renderer fallback. Loader tests cover deduplication/cache, independent and all-waiter cancellation, deadline, bounded retries, safe failures with explicit retry, dependency order, cycles, depth and transitive protocol conflicts. Existing registration/session and TypeScript headless checks remain required.

Existing manifests and Protocol schemas are unchanged; these are optional host services, never authored data. This repository's fixture drivers/host registrations do not assert actual WASM/framework or production engine compatibility. Explicit migration is required to change serialized contract versions; no data migration is needed for these optional entries. Decision: improvement-proposals/decisions/registry-resolution-v1.md.
